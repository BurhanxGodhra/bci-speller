# Project Narrative

The short version: this started as an 8-phase mentored build of a dual-paradigm BCI speller, went through the usual research-to-engineering translation problems, and then got extended into a Streamlit app meant to answer a harder question than "does the classifier work" — namely, could a real person plug in a real headset and actually calibrate this thing themselves. That second part surfaced most of the real bugs, because it's where the assumptions from offline research-data pipelines stop holding.

## Phases 1–2: environment and hardware abstraction

Phase 1 was scaffolding — repo structure, locked dependencies, and a display refresh-rate check that turned out to be more useful than expected. The first version of that check measured frame timing with a plain pygame window and reported 96Hz on a MacBook Air, which doesn't have a variable-refresh display at all. The bug: pygame's windowed surface isn't vsync-locked by default, so `clock.tick()` was just measuring OS scheduler noise, not real display timing. Switching to SDL2's `Renderer` with `vsync=True` didn't fully fix it either — it reported 131Hz, still physically impossible for that hardware. The actual fix was to stop trying to time a small windowed surface at all and ask macOS directly via `NSScreen.maximumFramesPerSecond()`, which correctly reported the panel's real fixed 60Hz. Lesson that stuck for the rest of the project: don't trust software-measured timing when there's an authoritative source you can just query.

Phase 2 built the hardware abstraction layer — LSL auto-discovery, a channel mapper that reconciles whatever electrodes a given headset has against what the paradigms need (with an explicit fallback table for headsets like the Muse that don't have true occipital electrodes), and a polyphase resampler to harmonize sample rates. Verified end-to-end against a synthetic mock LSL stream before any real classifier touched it.

## Phases 3–4: the actual classifiers

P300 used xDAWN spatial filtering plus shrinkage-LDA, trained on `BNCI2014009`. One naming correction worth recording: the original brief called for "BCI Competition III Dataset II," which isn't packaged under that name in MOABB — the closest available equivalent with the same paradigm (row/column flashing matrix) is `BNCI2014009`. First real run: 88.4% accuracy, 0.918 AUC, consistent across all 5 CV folds — no fold was a lucky outlier.

SSVEP compared CCA, FBCCA, and a supervised CNN on `Nakanishi2015`. FBCCA beat CCA by a solid margin (77.8% vs 70.4%), as expected from the original FBCCA paper. The CNN scored 7.4% — barely above the 8.3% chance level for 12 classes. That's not a bug: with 180 total epochs across 12 classes, there's roughly 10 examples per class, nowhere near enough for a CNN with no augmentation to learn anything. It's kept in the results specifically because it demonstrates, concretely, why CCA/FBCCA — which need no training data — are the standard choice for SSVEP.

## Phase 5–7: artifact rejection, UI, closed loop

Artifact rejection (amplitude threshold, peak-to-peak, sliding-window variance) got wired into the HAL's streaming interface. The pygame speller UI combined a P300 flash matrix, SSVEP flicker targets, and local GPT-2 predictive text — with keyboard input standing in for classifier output until the closed-loop phase. Phase 7 replaced the keyboard with real `pyautogui` injection driven by FBCCA classifying held-out labeled trials, plus a Wolpaw ITR calculation: 86.67% accuracy, 38.36 bits/min over 15 selections.

## Extending into the app: where the real debugging happened

The original 8-phase build proved the ML pipeline worked. The app was built to answer a different question: could this be made usable by someone who isn't the person who built it. That meant a browser-based stimulus renderer, a calibration wizard, and warm-start blending — and each of these surfaced a real architectural mistake that the CLI-only version never would have.

**The stimulus component's first version used a CDN script tag for `streamlit-component-lib`.** It threw `Streamlit is not defined` in the browser console. Cause: that npm package isn't built as a UMD bundle for direct `<script>` tag use — it's meant for bundlers. Fix was to drop the dependency and implement Streamlit's actual component message protocol directly via `postMessage`, which is a small, stable, undocumented-but-consistent contract (`streamlit:componentReady`, `streamlit:setFrameHeight`, `streamlit:setComponentValue`).

**The P300 calibration wizard's first version called the same keyed Streamlit component hundreds of times inside one blocking loop**, on the theory that repeated calls would animate it like a normal function call would. It threw `StreamlitDuplicateElementKey` on the second call. The actual rule: a Streamlit element registration happens once per script execution, full stop — there's no "call it again to update it" within a single run. The fix was a real architecture change: move the flash-timing/marker-pushing/EEG-recording loop into a background thread that just updates shared state, and have the Streamlit script itself rerun on a ~100ms cadence, calling the component exactly once per rerun. Marker timestamps (the actual ground truth for epoch extraction) come from the background thread directly and don't depend on how often the UI happens to redraw.

**Warm-start blending had two separate real bugs, not one.** First: `X has 1200 features but LinearDiscriminantAnalysis is expecting 1236` — the public prior model was trained on `BNCI2014009`'s ~257Hz epochs while personal calibration epochs were extracted at 250Hz, giving different timepoint counts after xDAWN flattening even with matching channel counts. Fixed by resampling to the prior model's exact timepoint count before scoring. Second, more subtle: after fixing that, blending at `weight=1.0` (which should be mathematically identical to personal-only) gave 81.7% accuracy for personal-only versus 43.3% for "blended," while AUC matched exactly (0.443 both). The AUC match was the tell — it meant the *ranking* of predictions was identical but the *threshold* wasn't. The blending code was z-scoring each model's decision scores by subtracting the training-set mean before combining, which shifts the effective decision boundary away from 0 (LDA's actual threshold) to wherever that mean happens to be. Fix: scale by standard deviation only, don't center by mean. After that, `weight=1.0` reproduced personal-only exactly, as it should.

**Separately, environment drift caused real friction more than once** — a fresh `.venv` created under Python 3.13 instead of 3.11 broke `torch==2.4.1` (no wheel for 3.13 at pin time), and `pylsl` failing to find its native `liblsl` binary needed `brew install labstreaminglayer/tap/lsl` plus an explicit `PYLSL_LIB` environment variable on macOS. Neither is a code bug, but both cost real debugging time and are exactly the kind of thing that makes "the pipeline works on my machine" not the same claim as "the pipeline works."

## What all of this adds up to

The CLI pipeline demonstrates the ML actually works on real public data. The app demonstrates something different and, for an actual product question, more important: that getting from "the algorithm is published and works on a benchmark dataset" to "a person can sit down and use this" surfaces a completely different category of bug — timing assumptions, framework execution models, numerical scale mismatches — none of which show up in an offline accuracy table. See `docs/decisions.md` for the itemized decision log behind each of these fixes.
